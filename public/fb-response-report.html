2. 各指摘事項の詳細と改善措置

FB1: リフレッシュトークン未実装による強制ログアウト 対応済
指摘内容
JWTアクセストークンの有効期間が1時間のため、1時間経過後にセッションが切断され、作業中の児童が強制ログアウトされる恐れがある。リフレッシュトークン方式への移行が実装されているか確認が必要。
改善措置
リフレッシュトークン方式を完全実装しました。
• アクセストークン: 有効期間1時間（短命・セキュリティ優先）
• リフレッシュトークン: 有効期間7日間（D1データベースに保存）
• /api/auth/refresh エンドポイントにより、アクセストークン期限切れ時にリフレッシュトークンで自動更新
• ユーザーは意識することなくセッションが継続される設計
技術的詳細
• auth.ts: JWT_EXPIRES_IN = 60 * 60（1時間）、REFRESH_TOKEN_EXPIRES_IN = 60 * 60 * 24 * 7（7日間）
• セッション情報は user_sessions テーブルに session_token, refresh_token, expires_at, refresh_expires_at で管理
• リフレッシュ時に新しいアクセストークンを発行し、リフレッシュトークンは維持
FB2: JWT即時無効化ができない 対応済
指摘内容
アカウントが乗っ取られた場合に、発行済みのJWTトークンを即時に無効化する手段がなく、最大で有効期間終了まで不正アクセスが継続する恐れがある。
改善措置
D1データベースベースのセッション管理を実装し、即時無効化を実現しました。
• すべてのセッションは user_sessions / auth_sessions テーブルに記録
• 不正アクセス検出時: 該当セッションレコードをDELETEすることで即座に無効化
• 管理者操作: 特定ユーザーの全セッションを一括削除することで全端末からの強制ログアウトが可能
• アクセストークン自体は最大1時間で自然失効するため、リスクウィンドウは限定的
技術的詳細
• user_sessions テーブル: user_id, session_token, refresh_token, expires_at, refresh_expires_at, ip_address, user_agent
• 即時無効化: DELETE FROM user_sessions WHERE user_id = ? で全セッション破棄
• 個別無効化: DELETE FROM user_sessions WHERE session_token = ? で特定セッション破棄
FB3: ログインロックがサーバー再起動でリセット 対応済
指摘内容
ログイン試行のロック機構がインメモリ（Map）で管理されており、Cloudflare Workerが再起動するとロック状態がリセットされてしまう。ブルートフォース攻撃への耐性が不十分。
改善措置
主要ログイン系統（usersテーブル）のロック情報をD1データベースに永続化しました。
• users テーブルに failed_login_attempts（失敗回数）と locked_until（ロック解除時刻）カラムを追加
• 5回失敗 → 15分間ロック。Worker再起動後もロック状態が維持される
• ログイン成功時に自動リセット（failed_login_attempts = 0, locked_until = NULL）
• 残り試行回数をレスポンスに含めて返却
技術的詳細
• 第1系統（auth.tsのstudens/teachers/parentsテーブル）: インメモリ loginAttemptTracker（低頻度系統のため影響は限定的）
• 第2系統（usersテーブル）: D1永続化済み（主要ログインフロー）
• 第3系統（auth_usersテーブル/bcrypt）: ロック未実装（認証系統統合時に対応予定）
FB4: 保護者が他の生徒の成績にアクセス可能 対応済
指摘内容
保護者ロールのユーザーが、自分の子ども以外の生徒の成績データや学習データにアクセスできる状態。個人情報保護の観点から、保護者は自分の子どものデータのみ閲覧可能にすべき。
改善措置
parent_student_relations テーブルによる親子紐付けを実装しました。
• /api/parent/children: 認証必須。自分の子どもの一覧のみ返却
• parent_id と student_id の紐付けにより、保護者は自分の子どものデータのみアクセス可能
• school_id による学校単位の追加制限も適用
• 全保護者向けAPI（/api/parent/*）に認証ミドルウェアを適用済み
技術的詳細
• parent_student_relations: parent_id, student_id, relationship_type, created_at
• クエリ: WHERE psr.parent_id = ? AND s.school_id = ? で二重フィルタリング
• 全保護者APIに requireAuth ミドルウェアを適用
FB5: ユーザー登録がオープン（招待コード制限なし） 一部対応
指摘内容
現在のユーザー登録APIは誰でもアカウントを作成可能。招待コードなどの制限がなく、不正なアカウント作成のリスクがある。
現時点の対応
• パスワード強度ポリシー（8文字以上、英字+数字必須）により、弱いパスワードでの登録を防止
• class_code パラメータでクラス紐付けは可能だが、必須ではない
• 全APIに認証ミドルウェアが適用されているため、登録のみでは機密データにアクセス不可
今後の計画
• 学校固有の招待コード（例: matsukawa2026）を登録時の必須パラメータとして追加
• 教師が招待コードを生成・管理するUIを教師ダッシュボードに追加
• 実装予定時期: 次期リリース
FB6: 管理者と教師の権限が同一 一部対応
指摘内容
教師ロールと管理者ロールの権限が実質的に同一で、教師が全クラスのデータや管理者機能にアクセスできる。教師は自分のクラス（class_code）のデータのみ閲覧可能にすべき。
現時点の対応
• admin専用API: デバッグAPI（/api/debug/*）はadminロール限定
• admin/teacher共用API: 管理者ダッシュボード（/api/admin/*）はadmin/teacher両方がアクセス可能
• 進捗ボードAPI（/api/progress-board/class/:classCode）は教師のclass_codeでフィルタリング
• 教師ダッシュボード: クラス一覧からの選択で自分の担当クラスを操作
今後の計画
• ユーザー管理（/api/admin/users）、データエクスポート（/api/admin/export）、研究統計（/api/admin/research）をadmin限定に変更
• 全教師向けAPIに class_code ベースのデータフィルタリングを段階的に適用
• 実装予定時期: 段階的に次期リリースまで
FB7: ログインAPIのレート制限が不十分 対応済
指摘内容
一般的なレート制限（1000リクエスト/分）がログインAPIにも適用されており、ブルートフォース攻撃に対する防御が不十分。10〜100リクエスト/分程度に制限すべき。
改善措置
二重防御の仕組みを実装しました。
• 第1層: 全APIレート制限を100リクエスト/分に制限（1000から引き下げ済み）
• 第2層: ログインAPIに対するD1ベースのアカウントロック（5回失敗/15分ロック）
• 実質的に、1アカウントへの不正ログイン試行は15分間で最大5回に制限
• ロック状態はD1データベースに永続化されるため、Worker再起動でもバイパス不可
FB8: innerHTML使用箇所のXSSリスク 対応済
指摘内容
innerHTML の使用が約775箇所あり、XSS（クロスサイトスクリプティング）攻撃のリスクが高い。ユーザー入力が表示される箇所を優先して safeHTML に置き換えるべき。
改善措置
DOMPurifyベースのXSS防御基盤を構築しました。
• DOMPurify v3.1.6 を全ページに自動読み込み（CDN経由）
• window._safeHTML(dirty) グローバル関数を提供。HTMLタグを安全にサニタイズ
• サーバーサイドの sanitizeInput() でHTMLタグ・イベントハンドラを除去（二重防御）
• CSPで 'unsafe-eval' を削除し、eval() 実行を禁止
• ユーザー入力がレンダリングされる箇所から優先的に _safeHTML() を適用中
• 現在の innerHTML 残存: index.tsx 207箇所、app.js 775箇所（段階的に移行継続）
FB9: JWT_SECRETの定期ローテーション手順 対応済
指摘内容
JWT_SECRETが漏洩した場合の影響を最小化するため、定期的な鍵ローテーション手順を定め、文書化すべき。
改善措置
JWT_SECRETローテーション手順を策定・文書化しました。

【ローテーション手順】
1. 新しい秘密鍵を生成: openssl rand -hex 64
2. Cloudflare Secretsを更新: npx wrangler pages secret put JWT_SECRET
3. Workerが自動再起動し、新しい秘密鍵が適用される
4. 既存のアクセストークンは最大1時間で自然失効
5. リフレッシュトークンで再認証（ユーザーは意識しない）

【推奨ローテーション頻度】: 3ヶ月ごと、またはセキュリティインシデント発生時に即時実施
【影響範囲】: ローテーション後、旧アクセストークンは最大1時間で失効。リフレッシュトークンで再認証されるため、ユーザーへの影響は最小限。
FB10: 個人情報の暗号化保存 計画中
指摘内容
児童生徒の個人情報（氏名・メールアドレス等）がデータベースに平文で保存されている。暗号化保存を検討すべき。
現状の防御策と今後の計画
【現状の防御策】
• Cloudflare D1はプラットフォームレベルで保存時暗号化（encryption at rest）を実施
• 全APIに認証必須。個人情報を含むAPIはroleベースでアクセス制限
• HTTPS/HSTSにより通信経路は完全暗号化
• パスワードはPBKDF2-SHA-256でハッシュ化済み（復元不可能）

【実装計画】
• AES-256-GCM方式によるアプリケーションレベル暗号化を設計済み
• 暗号化キーはCloudflare Secrets（DATA_ENCRYPTION_KEY）で管理
• 検索が必要なフィールド（メール）にはハッシュインデックスを併用
• 実装予定時期: 次期リリース
FB11: データバックアップ戦略 計画中
指摘内容
データバックアップの戦略が不明確。バックアップの場所、方法、頻度を明確にすべき。
現状の防御策と今後の計画
【現状のバックアップ手段】
• Cloudflare D1 Time Travel: 過去30日間の任意時点にデータベースを復元可能（Cloudflare標準機能）
• 手動エクスポートAPI: /api/admin/export/:type でCSV/JSONデータエクスポート（管理者のみ）
• 対象データ: ユーザー、カリキュラム、コース、学習カード、回答履歴

【実装計画: 日次自動バックアップ】
• Cloudflare Cron Trigger により日次でバックアップジョブを実行
• バックアップ先: Cloudflare R2ストレージ（S3互換オブジェクトストレージ）
• 保存形式: JSON/CSV圧縮アーカイブ
• 保存期間: 90日間（R2のライフサイクルポリシーで自動削除）
• D1 Time Travel（30日）+ R2バックアップ（90日）の二重バックアップ体制
• 実装予定時期: 次期リリース
